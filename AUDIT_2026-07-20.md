# Audit complet — AD Web Interface v1.45.0

**Date :** 2026-07-20 · **Périmètre :** `main` @ `c78a572` · ~24 000 lignes Python, 86 templates, 57 routes POST
**Contexte :** application Flask exposant la gestion d'un Active Directory, exécutée en service Windows **sur un contrôleur de domaine**, avec les droits d'un admin du domaine.

Ce contexte détermine la sévérité : ici, une élévation de privilège dans l'appli ≈ une élévation de privilège dans l'AD.

## 🔴 Critiques

### C1 — Contournement total du RBAC : tout utilisateur ayant *une* permission devient administrateur

**Fichiers :** `core/granular_permissions.py:217`, `routes/core.py:80-102`

`has_permission()` accorde l'accès dès qu'il existe **une intersection non vide** entre les permissions de l'utilisateur et les permissions requises :

```python
if entry_perms & required_permissions:
    return True
```

Or, les 64 routes protégées utilisent le nom *legacy* `'admin'`, qui est traduit en **l'intégralité** des permissions :

```python
'admin': list(ALL_PERMISSIONS.keys()),   # 30 permissions
```

Résultat : `require_permission('admin')` est satisfait par **n'importe quelle** permission unique. Aucune route n'utilise de nom granulaire — les seuls noms employés sont `admin` (64×), `write` (16×), `delete` (4×), tous des clés legacy à large périmètre.

**Ce n'est pas théorique.** Le fichier `data/permissions.json` versionné décrit un groupe d'équipe support doté de 10 permissions de gestion courante, dont aucune `admin:*`. Ce groupe dispose aujourd'hui, de fait, de l'accès complet aux 64 routes admin — dont :

- `POST /api/scripts/<nom>/execute` → **exécution de scripts PowerShell sur le contrôleur de domaine**
- `POST /api/security-fix`, `/api/log-analysis/auto-fix` → modifications système
- `/admin/settings`, `/admin/backups`, l'audit de sécurité, la suppression d'utilisateurs

**Correctif :** exiger l'inclusion, pas l'intersection, et cesser d'utiliser les alias legacy comme garde.

```python
# core/granular_permissions.py
if required_permissions <= entry_perms:      # au lieu de: entry_perms & required_permissions
    return True
```

L'inclusion seule casserait les routes `admin` (personne n'a les 30 permissions) — il faut donc **remplacer les 84 gardes par des permissions granulaires** : `@require_permission('admin:settings')`, `@require_permission('users:delete')`, etc. C'est le vrai chantier ; l'inclusion sans ce remplacement fermerait l'application.

Séquence recommandée :
1. Remplacer les gardes route par route (84 occurrences, mécanique).
2. Réserver `admin:*` aux routes réellement administratives ; en créer une nouvelle, `system:execute_script`, pour l'exécution PowerShell.
3. Puis seulement basculer sur l'inclusion et supprimer `LEGACY_PERMISSION_MAPPING`.
4. Ajouter un test qui échoue si un utilisateur `users:read` accède à une route admin.

### C2 — Historique d'audit d'un domaine réel publié dans un dépôt public

**Fichiers :** `data/audit_history/*.json` (26 fichiers versionnés)

Le `.gitignore` contient bien `data/audit_history/`, mais les fichiers ont été commités **avant** l'ajout de la règle : ils restent suivis et publics.

Chaque fichier est un rapport d'audit de sécurité complet du domaine, structuré en JSON. Sans en reproduire le contenu ici — ce document est lui-même destiné au dépôt — les champs exposés couvrent :

- les **paramètres de la politique de mot de passe** (longueur minimale, âge maximal, historique) ;
- le **nombre de comptes vulnérables au password spraying**, aux protocoles hérités, aux violations de tiering et aux délégations ;
- une liste `top_critical_issues` **nommant des comptes** et décrivant leur faiblesse précise, dont au moins un compte **administrateur signalé « sans mot de passe requis »**.

C'est un plan d'attaque prêt à l'emploi pour le domaine concerné.

> Les valeurs exactes ont été communiquées séparément à l'exploitant. Elles ne sont volontairement pas recopiées dans ce rapport, qui est versionné : reproduire les données fuitées dans le dépôt qu'on assainit annulerait la purge.

Sont également versionnés : `logs/*_diagnostic.json`, `logs/test_results/users_connected_*.json`.

**Correctif — dans cet ordre :**
1. Traiter les faiblesses décrites comme **déjà connues d'un attaquant** : le compte administrateur signalé « sans mot de passe requis » est à corriger côté AD immédiatement, indépendamment du code.
2. `git rm -r --cached data/audit_history logs/test_results logs/*_diagnostic.json` puis commit.
3. Purger l'historique (`git filter-repo --path data/audit_history --invert-paths`) et forcer le push — sachant que GitHub conserve des copies en cache et que le contenu a pu être indexé. La purge limite l'exposition future, elle n'annule pas l'exposition passée.
4. Ajouter un test CI qui échoue si `data/audit_history/` ou `logs/` redevient suivi.

### C3 — Validation des certificats TLS désactivée sur toutes les connexions LDAP

**Fichier :** `routes/core.py:29-33`

```python
_tls_config = Tls(
    validate=ssl.CERT_NONE,   # ← aucun certificat n'est vérifié
    ...
)
```

Toutes les connexions LDAPS (636) et STARTTLS acceptent n'importe quel certificat, y compris auto-signé par un attaquant. Le chiffrement est présent mais l'authentification du serveur est absente : un attaquant en position d'interception sur le réseau récupère **les identifiants d'administrateur du domaine** saisis dans le formulaire de connexion.

L'ironie est que l'application propose par ailleurs un bouton « Activer LDAPS automatiquement » et un script `configure_ldaps.ps1` — elle pousse à activer LDAPS tout en ne vérifiant pas ce que LDAPS garantit.

**Correctif :**
```python
_tls_config = Tls(
    validate=ssl.CERT_REQUIRED,
    version=_tls_version,
    ca_certs_file=os.environ.get('AD_CA_BUNDLE') or None,   # None → magasin système
    ciphers='HIGH:!aNULL:!eNULL:!EXPORT:!DES:!RC4:!MD5:!PSK:!SRP'
)
```
Prévoir un échappatoire explicite et bruyant (`AD_TLS_INSECURE=true` + bandeau d'avertissement dans l'UI) pour les DC à certificat auto-signé, plutôt qu'un défaut permissif silencieux. Documenter l'import du certificat racine de l'AD.

### C4 — Le mot de passe AD circule et réside dans le cookie de session

**Fichiers :** `core/session_crypto.py`, `routes/core.py:344-351`

Le mot de passe AD est chiffré (Fernet, PBKDF2-SHA256 100 000 itérations, sel aléatoire persisté — la cryptographie elle-même est correcte) puis stocké dans `session['ad_password']`. Flask utilise par défaut des sessions **côté client** : le chiffré part donc dans le cookie du navigateur, à chaque requête, et l'application ne configure aucun stockage serveur.

Conséquences :
- Compromission de `SECRET_KEY` + `data/crypto_salt.bin` → déchiffrement de tous les mots de passe capturés.
- Le cookie est un porteur d'identifiants AD complets, sans révocation possible côté serveur : la déconnexion vide le cookie, elle n'invalide rien.
- Sur un déploiement HTTP (voir É1), ce cookie transite en clair.

**Correctif :** passer à des sessions côté serveur (`Flask-Session` avec backend fichier ou Redis) ; le cookie ne porte plus qu'un identifiant opaque. Cela apporte en prime la révocation, l'expiration réelle et l'énumération des sessions actives. Alternative plus lourde mais plus propre à terme : ne pas conserver le mot de passe du tout et déléguer à Kerberos/SPNEGO.

## 🟠 Élevés

### É1 — Le cookie de session n'est pas `Secure` par défaut

`core/security.py:369` — `SESSION_COOKIE_SECURE` vaut `false` par défaut, avec ce commentaire : « Waitress sert en HTTP interne ». Combiné à C4, le cookie contenant les identifiants AD chiffrés transite en clair sur le LAN.

Incohérence associée : la même variable est lue avec un défaut `'true'` ligne 325 pour décider d'envoyer HSTS. L'application peut donc envoyer `Strict-Transport-Security` sur une connexion HTTP — ce qui, si le service n'est pas joignable en HTTPS, rend le site inaccessible depuis les navigateurs l'ayant mis en cache.

**Correctif :** un seul point de vérité (`FORCE_HTTPS`), défaut `Secure=true`, HSTS émis uniquement si `request.is_secure`.

### É2 — L'ordre des méthodes de connexion privilégie le LDAP en clair

`routes/core.py:200-205` :

```python
methods = [
    (389, False, ntlm_user, NTLM,   "NTLM",        False),  # ← essayé en premier, sans TLS
    (389, False, upn_user,  SIMPLE, "STARTTLS",    True),
    (636, True,  ntlm_user, NTLM,   "LDAPS-NTLM",  False),
    (636, True,  upn_user,  SIMPLE, "LDAPS-SIMPLE",False),
]
```

Le premier essai retenu fixe `session['ad_port']`/`ad_use_ssl` pour **toute la durée de la session**. En pratique, sur un DC acceptant NTLM sur 389, l'application travaille en permanence en clair : listes d'utilisateurs, appartenances aux groupes, mots de passe LAPS, clés de récupération BitLocker.

NTLM ne révèle pas le mot de passe (défi/réponse), mais tout le trafic applicatif suivant est lisible sur le réseau.

**Correctif :** inverser l'ordre (LDAPS → STARTTLS → LDAP clair) et n'autoriser le dernier palier que si `AD_ALLOW_INSECURE_LDAP=true` est explicitement positionné.

### É3 — 24 routes POST/DELETE sans protection CSRF

La protection existe (`validate_csrf_token`) mais est appliquée **manuellement, route par route**, et 24 routes mutatives l'ont oubliée :

```
/api/scripts/<script_name>/execute        ← exécution PowerShell
/api/security-fix
/api/log-analysis/auto-fix
/tools/locked-accounts/unlock
/tools/recycle-bin/<dn>/restore
/groups/<dn>/remove-member
/tools/api-docs/generate-key
/tools/api-docs/revoke-key
… (16 autres)
```

`SameSite=Lax` bloque l'envoi du cookie sur un POST cross-site, ce qui atténue fortement l'exploitation directe depuis un site tiers — mais cette protection est un filet de sécurité du navigateur, pas un contrôle applicatif, et elle ne couvre pas les scénarios same-site (XSS stocké, sous-domaine compromis, cf. M4).

**Correctif :** remplacer l'approche manuelle par une protection globale — `Flask-WTF` (`CSRFProtect(app)`) ou un `@app.before_request` qui refuse toute méthode mutative sans jeton valide, avec liste d'exemption explicite. Une protection qu'il faut penser à appliquer sera oubliée à nouveau.

### É4 — Comparaison de jeton CSRF non constante en temps

`core/security.py:393` — `return token and token == session.get('csrf_token')`.
→ `hmac.compare_digest(str(token), str(session.get('csrf_token', '')))`.

### É5 — Mise à jour automatique sans vérification de signature, suivant `main`

`core/updater.py:45` — l'updater télécharge `https://github.com/<repo>/archive/refs/heads/main.zip`, extrait, écrit sur disque, lance `pip install --upgrade`, puis redémarre le service.

Deux problèmes distincts :
1. **Aucune vérification d'authenticité.** Les SHA256 calculés servent à décider quels fichiers ont changé (diff), pas à valider une source de confiance. Toute compromission du dépôt GitHub, ou un push malveillant, se propage automatiquement en exécution de code sur tous les contrôleurs de domaine équipés.
2. **Suivi de branche, pas de version.** N'importe quel commit sur `main` — y compris un travail en cours — est déployé chez les clients. Le champ « Dernière version » du README, désynchronisé de `VERSION`, illustre que ce flux n'est pas piloté par des releases.

**Correctif :** publier des **releases GitHub signées** (tags + GPG ou Sigstore), consommer `refs/tags/vX.Y.Z` et non `heads/main`, vérifier la signature avant extraction. À défaut de signature, au strict minimum : épingler sur les tags de release et publier un manifeste SHA256 signé hors bande.

### É6 — `pip install --upgrade` élargit silencieusement les dépendances

`core/updater.py:258` — `pip install -r requirements.txt --upgrade` est exécuté à chaque mise à jour. Les versions sont épinglées (`==`) sauf `packaging>=23.0`, donc la surface est limitée, mais `--upgrade` sur un requirements épinglé n'apporte rien et masquera tout dépinglage futur.

Par ailleurs les versions épinglées datent de novembre 2025 et accusent du retard : `cryptography==41.0.7`, `requests==2.31.0`, `Werkzeug==3.0.1`, `flask==3.0.0`, `waitress==2.1.2`. Plusieurs CVE ont été publiées depuis sur ces branches.

**Correctif :** retirer `--upgrade` ; mettre à jour l'ensemble des épingles ; activer Dependabot (le dépôt a déjà `.github/`).

## 🟡 Moyens

### M1 — Filtres LDAP non échappés (9 emplacements)

L'échappement est correctement appliqué dans la majorité du code, mais ces appels interpolent directement :

| Fichier | Ligne | Variable |
|---|---|---|
| `core/security_audit.py` | 498, 526, 551 | `account`, `group` |
| `routes/ous/__init__.py` | 222 | `dn` |
| `routes/groups/__init__.py` | 455 | `dn` |
| `routes/users/password.py` | 36 | `dn` |
| `routes/users/helpers.py` | 50 | `dn` |
| `password_audit/admin.py` | 158 | `pattern` |
| `routes/admin_tools.py` | 378 | `safe_base_dn` |

Les valeurs `dn` proviennent de segments d'URL `<path:dn>` — donc contrôlées par le client. L'impact est une injection de filtre LDAP (contournement de portée de recherche, divulgation d'attributs), pas une écriture.

**Correctif :** `escape_ldap_filter()` sur chacun. Mieux : un helper `ldap_search()` unique qui échappe ses paramètres, pour que le cas non échappé cesse d'être exprimable.

### M2 — `escape_ldap_filter` et `sanitize_dn_component` sont approximatifs

`core/security.py:15-54`. Deux défauts :
- `LDAP_ESCAPE_CHARS` inclut `/` (inutile, RFC 4515 ne le demande pas) et manque le traitement des octets non-ASCII.
- `sanitize_dn_component` **supprime** les caractères au lieu de les échapper (RFC 4514). « O'Brien, John » devient « O'Brien John » : perte de données silencieuse sur des noms légitimes, ce qui produira des créations de comptes incorrectes.

**Correctif :** utiliser `ldap3.utils.conv.escape_filter_chars` et `escape_rdn`, déjà présents dans la dépendance.

### M3 — Vérification de chemin par préfixe de chaîne

`core/path_security.py:27` — `str(target_resolved).startswith(str(base_resolved))`.
`/opt/app/data-evil` passe le contrôle pour une base `/opt/app/data`.
→ `target_resolved.is_relative_to(base_resolved)` (Python 3.9+).

### M4 — XSS stocké via `custom_css`

`templates/base.html:47` — `{{ site_settings.custom_css|safe }}` est injecté dans un bloc `<style>`. Une valeur contenant `</style><script>…</script>` s'exécute. Le réglage est accessible via `/admin/settings`, donc — via C1 — atteignable par tout utilisateur disposant d'une permission quelconque.

**Correctif :** valider le CSS (rejeter `<`, `</style`, `expression(`, `javascript:`) ou servir la feuille via une route dédiée avec `Content-Type: text/css`, ce qui la sort du contexte HTML.

### M5 — `request.endpoint` peut être `None` → 500 dans le rate limiter

`core/security.py:205` — `request.endpoint.startswith('api_')` lève `AttributeError` quand aucune route ne correspond (404), exactement au moment où le rate limiter est le plus sollicité (scan). Un attaquant peut ainsi transformer un dépassement de quota en erreur 500.
→ `(request.endpoint or '').startswith('api_')`.

### M6 — Le rate limiting repose sur `request.remote_addr`

Derrière un reverse proxy (Authelia, IIS, nginx — architecture documentée du projet), `remote_addr` est l'IP du proxy. Tous les utilisateurs partagent alors un compteur unique : soit un attaquant verrouille tout le monde, soit le quota est inopérant.
**Correctif :** `werkzeug.middleware.proxy_fix.ProxyFix` avec un nombre de sauts configuré, en s'appuyant sur `TRUSTED_PROXIES` qui existe déjà dans `config.py` mais n'est jamais utilisé.

### M7 — État du rate limiting non protégé par verrou et volatile

`core/security.py:60-86` — les dictionnaires `_login_attempts` / `_action_attempts` sont mutés depuis 8 threads Waitress sans verrou (`_cleanup_old_attempts` reconstruit les dictionnaires pendant que d'autres threads y écrivent), et tout l'état disparaît au redémarrage — un attaquant peut réinitialiser son quota en provoquant un redémarrage via l'updater.
Note : `threading.Lock()` a déjà été introduit pour `_update_progress` en v1.39.0 (C3) ; le même raisonnement s'applique ici.

### M8 — `get_rate_limit_status` ignore ses propres paramètres

`core/security.py:181-184` — valeurs `5` et `300` codées en dur alors que les décorateurs utilisent d'autres seuils. L'UI affiche donc un statut faux dès qu'un quota non standard est employé.

### M9 — CSP avec `'unsafe-inline'` sur les scripts

`core/security.py:342` — `script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net`. Avec 90 usages de `innerHTML` dans les templates, la CSP n'apporte pratiquement aucune protection XSS. Migrer vers des nonces (`'nonce-<random>'` généré par requête) et héberger localement les ressources CDN — ce qui supprime au passage une dépendance réseau externe sur un contrôleur de domaine, souvent isolé.

## Ce que le code fait bien

Pour situer les constats ci-dessus, plusieurs choix sont solides et méritent d'être préservés :

- **Dérivation de clé correcte** : PBKDF2-SHA256, 100 000 itérations, sel aléatoire de 32 octets persisté par déploiement (`session_crypto.py`) — nettement au-dessus de ce qu'on rencontre habituellement.
- **`subprocess` sans `shell=True`** partout, avec allowlist des scripts au niveau des routes : l'injection de commande directe n'est pas possible.
- **Discipline sur les connexions LDAP** : les correctifs v1.44.0 (`finally: conn.unbind()`) et les `size_limit` montrent une reprise en main réelle des fuites de ressources.
- **Mise à jour avec staging, écriture atomique, sauvegarde et rollback sur échec de healthcheck** : l'ingénierie du mécanisme est sérieuse ; c'est uniquement la confiance en la source qui manque (É5).
- **Base de tests présente** (~2 700 lignes) — un point d'appui pour les non-régressions demandées en C1.

## Une remarque de fond

Trois des quatre constats critiques ont la même forme : **un mécanisme de sécurité est présent, bien intentionné, mais désarmé par son propre défaut permissif.** Le RBAC existe et accorde tout ; TLS est configuré et ne valide rien ; le `.gitignore` couvre l'historique d'audit qui reste néanmoins publié.

L'enjeu n'est donc pas d'ajouter des protections — l'architecture en comporte déjà beaucoup — mais de faire en sorte que **le défaut soit le comportement sûr**, et que le mode permissif exige une action explicite et visible. C'est ce principe qui guide les correctifs proposés ci-dessus.
